# Join integration

`/join` shows the WhatsApp sign-in card and an optional flight. One Boarding pass button opens the scanner, screenshot upload and manual flight entry together. Sending LOGIN/START in WhatsApp is the opt-in; there is no consent checkbox or role picker. With a flight, it requests a single-use token from `/api/join`, then shows the returned WhatsApp link and Wallet button. Without a flight, it opens a plain START message so the passenger can add the flight in WhatsApp. TODO(join-api): both server token endpoints still require a scheduled flight; accepting flightless POSTs requires changes outside the join-page ownership. `/join/qr` renders the public entry URL. Sharing preserves the flight and backend override. The Română / English switch controls page copy and sends `lang` with both join requests (Romanian by default). The single-use token carries that choice into the WhatsApp profile at START; writing English/EN or Română/RO changes it later, including on the personal page.

Scanning runs locally with native PDF417/Aztec support and a JavaScript fallback; name, PNR, raw barcode and images are never submitted. The first leg is used and nearest-year date inference remains editable. `WalletButton` posts the join token or an active subscription ID to `/api/wallet/pass`. Configure `VITE_PUBLIC_URL` for QR/share links reachable on phones.

`Boarding pass demo` posts `{lang: "ro" | "en"}` to the public Worker endpoint `/api/join/demo` (optional `flight` and `name`). It selects the first scheduled departure from the same Unity/provisional schedule used by `/api/join`, creates a one-leg 60-character M1 BCBP and a normal single-use join token, and returns `{bcbp, token, waLink, walletUrl}`. The white demo card draws that exact BCBP as PDF417 using pinned `bwip-js`. Native PDF417/Aztec detection is used where available; a pinned, lazily loaded ZXing decoder handles other browsers. Screenshot decoding is tested against the actual rendered barcode pixels. Physical phone-to-phone camera scanning still needs a device check with camera permission and HTTPS.

Unity's schedule currently carries seconds since midnight, without a calendar date or destination airport code field. Demo departures use today's **Europe/Bucharest** date (with day rollover for times over 24 hours). Known provisional destination labels are explicitly mapped to IATA codes; explicit three-letter codes are accepted and unknown labels fail rather than guessing an airport. No entry-slot time is supplied by this endpoint yet; the Wallet builder supports `Ora estimată la intrare: HH:MM` when one is available.

With Wallet credentials configured, demo passes default to `flightClasses`/`flightObjects`, with one class per flight/date, PDF417 BCBP and the `Clarion pe WhatsApp` link. Existing subscription/join passes without boarding data retain the generic implementation. `WALLET_PASS_KIND=generic` forces the generic pass, and local flight JWT build/sign errors attempt that fallback. Missing credentials use the existing local Wallet demo URL; the barcode remains visible on `/join` regardless.

The save-link flow does **not** contact Google during generation: a valid RS256 JWT and passing shape tests do not establish issuer permission, class approval or successful saving on a real Google account. Save-time rejection cannot automatically trigger the local catch; set the Worker's `WALLET_PASS_KIND` variable to `generic` and generate again. No live Wallet save has been verified by the tests.

Schema references: [FlightClass](https://developers.google.com/wallet/reference/rest/v1/flightclass), [FlightObject](https://developers.google.com/wallet/reference/rest/v1/flightobject), [IATA BCBP implementation guide](https://www.iata.org/contentassets/1dccc9ed041b4f3bbdcf8ee8682e75c4/2021_03_02-bcbp-implementation-guide-version-7-.pdf). Local scheduled departure is sent without a UTC offset, as required by Google.

Logout clears the local session and sign-in state even when server revocation fails. The LOGIN regression forces a failed request and checks storage and reload; the smoke script also verifies successful server revocation using the real signed webhook flow. A failed revocation leaves the server token valid until expiry, but removes it from this browser.
